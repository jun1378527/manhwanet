## 1. 작성 정책

### 1.1 리뷰 개수와 별점과의 관계

- **[확정]** 사용자·작품당 리뷰는 1개입니다. 다시 쓰고 싶으면 수정합니다. 삭제 후 다시 작성하면 새 리뷰입니다(새 `id`, 새 `created_at`, `version` 0, 목록 맨 앞).
- **[확정]** 리뷰는 별점과 독립입니다.
  - `work_reviews`는 `work_ratings`를 참조하지 않고, 별점 삭제가 리뷰에 영향을 주지 않습니다(반대도 같음).
  - `review`와 `rating` 패키지는 서로 import하지 않습니다.
- **[확정]** 리뷰 응답에 작성자의 별점을 넣지 않습니다. **[기존]** 별점 명세는 개인 별점을 공개하지 않고 집계만 공개합니다.

### 1.2 본문 — 정규화·검증 순서

**[확정]** 서버(`ReviewBody.normalize`)는 다음 순서로 처리합니다. 실패하면 400 `INVALID_INPUT`, `fieldErrors[body]`입니다.

| 순서 | 처리 | 실패 시 `reason` |
|---|---|---|
| 1 | 누락·JSON `null` | "리뷰 내용을 입력해 주세요." |
| 2 | JSON 문자열이 아님(숫자·불리언·배열·객체) | "리뷰 내용은 문자열이어야 합니다." |
| 3 | 원시 입력 UTF-16 길이 10,000 초과 (정규화 비용 제한) | "리뷰는 10자 이상 2,000자 이하로 입력해 주세요." |
| 4 | 줄바꿈 통일: `\r\n` → `\n`, 남은 `\r` → `\n` | — |
| 5 | 금지 문자: `\n`(U+000A)·`\t`(U+0009)를 뺀 C0 제어 문자(U+0000~U+001F), DEL(U+007F), C1 제어 문자(U+0080~U+009F) | "사용할 수 없는 문자가 포함되어 있습니다." |
| 6 | 앞뒤 공백 제거: `String.strip()` (유니코드 공백, 전각 공백 U+3000, 앞뒤 줄바꿈·탭 포함) | — |
| 7 | 공백만 있었음(제거 후 0자) | "리뷰 내용을 입력해 주세요." |
| 8 | 제거 후 길이가 10~2,000 **코드 포인트** 밖 | "리뷰는 10자 이상 2,000자 이하로 입력해 주세요." |

- 금지 문자 검사(5)를 공백 제거(6)보다 먼저 합니다. `U+000B`, `U+001C~U+001F`처럼 Java가 공백으로 보는 제어 문자가 앞뒤에 있어도 조용히 지워지지 않고 거절됩니다.
- PostgreSQL `TEXT`는 `U+0000`(NUL)을 저장할 수 없어 DB 오류(500)가 나므로 애플리케이션이 반드시 먼저 거절합니다.
- 공백 판정은 `String.strip()`(`Character.isWhitespace`)을 따릅니다. 줄바꿈 없는 공백(U+00A0, U+2007, U+202F)은 공백으로 보지 않아 남습니다. **[기존]** 작품 제목·닉네임 규칙과 같습니다.
- 본문 **가운데**의 공백·빈 줄·탭은 그대로 둡니다.
- **[확정]** 유니코드 정규화(NFC 등)는 하지 않습니다. 조합형(`e` + U+0301)은 2 코드 포인트로 저장·계산됩니다. **[기존]** 작품 제목도 정규화하지 않습니다.
- 길이는 코드 포인트입니다. 이모지 1개(서로게이트 쌍)는 1자이고, ZWJ·피부색 조합 이모지는 구성 코드 포인트 수만큼 셉니다. 화면 글자 수 표시도 코드 포인트(`[...text].length`)로 셉니다.
- U+2028·U+2029(줄·문단 구분자), 양방향 제어 문자(U+202A~202E, U+2066~2069)는 제어 문자(Cc)가 아니므로 허용합니다. 화면은 본문을 `dir="auto"` + `unicode-bidi: isolate`로 감싸 주변 UI로 번지지 않게 합니다.
- 최소 10자는 애플리케이션만 검사합니다(DB에는 1자 이상·2,000자 이하와 공백 아님만 둠, §2).

### 1.3 스포일러

- **[확정]** 작성자가 `containsSpoiler`(JSON 불리언)로 표시합니다. 자동 판별은 하지 않습니다.
- **공개 목록 API는 스포일러 리뷰의 본문을 포함해 그대로 응답합니다.** 리뷰는 누구나 읽을 수 있는 공개 데이터이며, 스포일러 숨김은 **원치 않는 노출을 줄이는 화면 표시 정책**일 뿐 접근 통제가 아닙니다. API를 직접 호출하거나 화면에서 펼치면 누구나 본문을 볼 수 있습니다.
- 공개 화면은 스포일러 리뷰 본문을 기본으로 접고(본문을 DOM에 렌더링하지 않음), 사용자가 "내용 보기"를 눌러야 보여 줍니다. 펼친 상태는 기억하지 않습니다.
- 내 리뷰 영역(작성자 본인)에서는 접지 않습니다.

### 1.4 형식

- **[확정]** 일반 텍스트만 받습니다. 저장은 정규화한 원문 그대로 하고, HTML 이스케이프는 **출력할 때** 합니다(저장 시 이스케이프하지 않음). `<script>` 같은 문자열도 입력한 글자 그대로 저장·응답됩니다.
- 화면은 React 텍스트 노드로만 출력하고 `white-space: pre-wrap`으로 줄바꿈을 보여 줍니다. `dangerouslySetInnerHTML`, 링크 자동 변환, Markdown은 쓰지 않습니다.
- HTML·Markdown·링크 자동 변환은 후속 기능입니다.

## 2. 데이터 모델 — `V5__create_work_reviews.sql`

```sql
CREATE TABLE work_reviews (
    id               BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id          BIGINT      NOT NULL,
    work_id          BIGINT      NOT NULL,
    body             TEXT        NOT NULL,
    contains_spoiler BOOLEAN     NOT NULL,
    version          BIGINT      NOT NULL DEFAULT 0,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_work_reviews_user FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE RESTRICT,
    CONSTRAINT fk_work_reviews_work FOREIGN KEY (work_id) REFERENCES works (id) ON DELETE CASCADE,
    CONSTRAINT uk_work_reviews_user_work UNIQUE (user_id, work_id),
    CONSTRAINT ck_work_reviews_body_length CHECK (char_length(body) BETWEEN 1 AND 2000),
    CONSTRAINT ck_work_reviews_body_not_blank CHECK (btrim(body) <> ''),
    CONSTRAINT ck_work_reviews_version CHECK (version >= 0),
    CONSTRAINT ck_work_reviews_updated_at CHECK (updated_at >= created_at)
);

CREATE INDEX idx_work_reviews_work_created ON work_reviews (work_id, created_at DESC, id DESC);
```

| 요소 | 근거 |
|---|---|
| `uk_work_reviews_user_work` | 사용자·작품당 1개를 DB가 보장. 동시 작성의 충돌 대상(§4.3). `user_id`가 앞이라 내 리뷰 조회·사용자 FK 검사에도 사용 |
| `idx_work_reviews_work_created` | 작품별 목록을 정렬 순서대로 읽고, 작품별 `COUNT(*)`에도 사용 |
| `ck_work_reviews_body_length` | 상한 2,000을 DB도 보장. UTF-8 DB에서 `char_length`는 코드 포인트 수로 Java `codePointCount`와 같음 |
| `ck_work_reviews_body_not_blank` | 공백만 있는 값 거부. **[기존]** `btrim`은 U+0020만 제거하므로 최후의 안전장치이며, 유니코드 공백은 애플리케이션이 책임짐 |
| `ck_work_reviews_version` | 음수 버전 거부 |
| `ck_work_reviews_updated_at` | 시각 정책(§2.1)을 DB가 보장. **[기존]** 별점과 같음 |
| 작품 FK CASCADE | **[기존]** `work_titles`, `work_creators`, `work_ratings`와 같음 |
| 사용자 FK RESTRICT | **[기존]** 별점 D-5와 같음. 회원 탈퇴 설계 때 재검토 |

- **[기존]** V1~V4는 수정하지 않습니다. 다른 도메인은 ID 값(`userId`, `workId`)으로만 참조하고 JPA 연관관계를 두지 않습니다.
- `contains_spoiler`는 기본값을 두지 않습니다. 애플리케이션이 항상 명시적으로 넣습니다.
- 쓰기는 모두 SQL로 하므로 엔티티 `WorkReview`는 읽기 전용(`@Immutable`)이고 JPA Auditing(`BaseTimeEntity`)·JPA `@Version`을 쓰지 않습니다. 버전 비교는 §4.4의 잠금 조회로 합니다.

### 2.1 시각·버전 정책

| 동작 | `created_at` | `updated_at` | `version` |
|---|---|---|---|
| 작성(INSERT) | 작성 시각 | = `created_at` | 0 |
| 본문 또는 스포일러 여부 변경 | 유지 | `GREATEST(기존 updated_at, now())` | +1 |
| 같은 내용으로 수정 요청(ID·버전 일치) | 유지 | 유지 | 유지 (200, 변경 없음) |
| 삭제 | 행 삭제 | 행 삭제 | — |
| 삭제 후 다시 작성 | 새 작성 시각 | 새 작성 시각 | 0 (새 `id`) |

- 시각은 **[기존]** 별점과 같이 PostgreSQL `now()`(트랜잭션 시작 시각)입니다. 동시 요청에서 되돌아가지 않도록 수정 시 `GREATEST`를 씁니다.
- 수정 여부는 `updated_at > created_at`로 판단해 응답 `edited`로 줍니다.
- **목록 순서는 `created_at` 기준이므로 수정해도 작성순이 바뀌지 않습니다.**
- `version`은 `BIGINT`입니다. 수정할 때마다 1씩 늘며, 상한(2^63−1)에 도달하는 것은 현실적으로 고려하지 않습니다.

## 3. 패키지와 의존 방향

```
review ──▶ work   (WorkService.exists)
review ──▶ user   (UserService.findNicknames — 새 공개 메서드)
review ──▶ auth   (AuthenticatedUser.id())
work   ──✗ review
user   ──✗ review
review ──✗ rating (서로 모름)
```

| 위치 | 타입 | 역할 |
|---|---|---|
| `user.application` | `UserService.findNicknames(Collection<Long>): Map<Long, String>` | ID 목록의 닉네임을 SQL 1개(`IN`)로 읽음. 빈 입력은 SQL 없이 빈 결과. 없는 ID는 결과에 없음 |
| `work.application` | `WorkService.exists(Long)` (**[기존]**) | 작품 존재 확인 |
| `review.application` | `ReviewService` | 내 리뷰 조회·작성·수정·삭제. `WorkService`, `WorkReviewRepository`에 의존 |
| `review.application` | `ReviewQueryService` | 공개 목록. `WorkService`, `UserService`, `WorkReviewRepository`에 의존 |
| `review.domain` | `WorkReview`(읽기 전용 엔티티), `WorkReviewRepository`, `ReviewBody` | |
| `review.dto` | 요청·응답 record, JSON 토큰 종류를 확인하는 필드 타입 | |
| `review.api` | `MyReviewController`(`/me/reviews`), `WorkReviewController`(`/works/{workId}/reviews`) | 경로는 `works` 아래지만 컨트롤러는 `review`에 둡니다. `work` 패키지는 바뀌지 않습니다 |

- **[기존]** 다른 도메인의 Repository·테이블을 직접 조회하지 않습니다. `review`는 `UserRepository`나 `users` 테이블(SQL `JOIN users` 포함)을 쓰지 않고 `UserService`만 씁니다.
- **[기존]** `UserService.getUser`는 없는 사용자에 401을 던지는 로그인용이므로 재사용하지 않습니다.
- 닉네임을 리뷰에 복사(스냅샷)하지 않습니다. 항상 현재 닉네임을 보여 줍니다.
- 빈 순환 없음: `ReviewService → WorkService`, `ReviewQueryService → WorkService, UserService`. `work`·`user`는 `review`를 import하지 않습니다.

## 4. 목록과 동시성

### 4.1 공개 목록 정렬·페이지

- **[확정]** 정렬은 `created_at DESC, id DESC` **고정**입니다. `sort` 파라미터는 받지 않습니다(보내도 무시).
- 페이지: `page` 0부터(기본 0), `size` 1~50(**기본 10**). 범위 밖이면 400 `INVALID_INPUT`(`fieldErrors[page]`·`[size]`). offset(`page × size`)이 int 범위를 넘는 `page`도 400("page가 너무 큽니다.")입니다. 마지막 페이지를 넘는 `page`는 빈 `content`(200).
- 응답은 **[기존]** `PageResponse`(`totalElements` = 그 작품의 리뷰 수)입니다.
- **보장 범위**: 같은 데이터에서 순서는 결정적입니다(`id` 보조 기준). offset 방식이므로 페이지를 넘기는 사이에 리뷰가 추가·삭제되면 항목이 밀려 중복되거나 빠져 보일 수 있습니다.

### 4.2 작성자 일괄 조회와 N+1 방지

공개 목록 1회 요청의 SQL:

1. 작품 존재 확인 (`WorkService.exists`)
2. 리뷰 페이지 (`WHERE work_id = ? ORDER BY created_at DESC, id DESC LIMIT ? OFFSET ?`)
3. 전체 개수 (`COUNT(*) WHERE work_id = ?`) — Spring Data는 첫 페이지가 다 차지 않는 등 개수를 이미 알 수 있으면 이 SQL을 생략합니다
4. 작성자 닉네임 일괄 조회 (`UserService.findNicknames`, 페이지의 `user_id`를 모아 `IN` 1회). 페이지가 비면 생략

- 보장하는 것은 "항상 SQL 4개"가 아니라 **리뷰·작성자 수가 늘어도 요청당 SQL 수가 늘지 않는 것**(N+1 없음)입니다. 테스트는 같은 페이지 크기에서 데이터가 적을 때와 많을 때의 SQL 수를 비교합니다.
- 닉네임이 결과에 없는 작성자(사용자 FK RESTRICT라 정상적으로는 없음)는 `author.nickname: null`로 응답하고, 화면은 "알 수 없는 사용자"로 표시합니다.

### 4.3 동시 작성

```sql
INSERT INTO work_reviews (user_id, work_id, body, contains_spoiler, version, created_at, updated_at)
VALUES (:userId, :workId, :body, :containsSpoiler, 0, now(), now())
ON CONFLICT ON CONSTRAINT uk_work_reviews_user_work DO NOTHING
```

- 영향받은 행이 0이면 이미 리뷰가 있으므로 409 `REVIEW_ALREADY_EXISTS`이고 아무것도 바꾸지 않습니다. 성공하면 같은 트랜잭션에서 행을 다시 읽어 응답합니다.
- `DO NOTHING`은 유니크 위반 예외를 내지 않으므로 트랜잭션이 중단되지 않습니다. 다른 트랜잭션의 미커밋 INSERT·DELETE와 충돌하면 그 결과를 기다린 뒤 판단합니다(PostgreSQL 유니크 인덱스 동작). 같은 사용자의 동시 POST는 하나만 201, 나머지는 409입니다.
- 작품 FK 위반(존재 확인 후 작품 삭제)은 **[기존]** 규칙대로 예상한 제약 이름 `fk_work_reviews_work`만 404 `WORK_NOT_FOUND`로 바꾸고, 그 밖의 무결성 오류는 500입니다.

### 4.4 수정·삭제 충돌 — D-6 (변경 확정)

- **[확정]** PUT은 **본문**에, DELETE는 **query**에 `reviewId`와 `version`을 함께 보냅니다. DELETE는 요청 본문을 쓰지 않습니다.
- **두 값이 현재 리뷰와 모두 같을 때만** 변경합니다. `version`만 비교하지 않는 이유: 삭제 후 다시 작성하면 새 리뷰도 `version` 0에서 시작하므로, 삭제 전 리뷰를 보고 만든 오래된 요청이 새 리뷰를 바꾸거나 지울 수 있기 때문입니다. `reviewId`는 IDENTITY라 다시 쓰이지 않습니다.

처리 (한 트랜잭션, READ COMMITTED):

1. `SELECT … FROM work_reviews WHERE user_id = :userId AND work_id = :workId FOR UPDATE`
2. 행이 있으면
   - `id`와 `version`이 요청과 모두 같으면: PUT은 내용이 같으면 변경 없이 200, 다르면 `UPDATE … SET body, contains_spoiler, version = version + 1, updated_at = GREATEST(updated_at, now()) WHERE id = :id` 후 다시 읽어 200. DELETE는 `DELETE … WHERE id = :id` 후 204
   - 하나라도 다르면 409 `REVIEW_VERSION_CONFLICT`, 변경 없음
3. 행이 없으면 **새 문장으로 한 번 더** 같은 행을 잠금 조회합니다.
   - READ COMMITTED에서 잠금 대기 중이던 행이 삭제되면 1의 결과는 비지만, 그 사이 커밋된 새 리뷰는 1의 스냅샷에 보이지 않습니다. 새 문장은 새 스냅샷이라 그 리뷰를 찾습니다.
   - 찾으면 2와 같이 비교합니다(새 리뷰는 `id`가 다르므로 409).
   - 그래도 없으면 PUT은 404 `REVIEW_NOT_FOUND`, DELETE는 204입니다.

- 잠금(`FOR UPDATE`)이 확인부터 변경까지 같은 행의 다른 수정·삭제를 막으므로 확인과 변경이 원자적입니다.
- `If-Match`/`ETag` 헤더는 쓰지 않습니다. **[기존]** 같은 출처 프록시가 넘기는 요청 헤더가 `Accept`, `Accept-Language`, `Content-Type`, `X-XSRF-TOKEN`뿐이기 때문입니다.

### 4.5 경쟁별 결과와 보장 범위

| 경쟁 | 결과 |
|---|---|
| 같은 사용자 동시 POST | 하나 201, 나머지 409 `REVIEW_ALREADY_EXISTS`. 행 1개 |
| 같은 `reviewId`·`version`으로 동시 PUT | 하나 200(`version`+1), 나머지 409. 남는 본문은 성공한 요청의 값 |
| 같은 `reviewId`·`version`으로 PUT·DELETE 동시 | 먼저 잠근 쪽만 성공. PUT 먼저 → 리뷰 수정됨, DELETE 409. DELETE 먼저 → 리뷰 없음, PUT 404 |
| 삭제 후 재작성된 리뷰에 오래된 PUT·DELETE | 409 (`reviewId` 불일치). 새 리뷰는 바뀌지 않음 |
| 삭제된 뒤(재작성 없음) 오래된 PUT | 404 `REVIEW_NOT_FOUND` |
| 삭제된 뒤(재작성 없음) 오래된 DELETE | 204 (이미 없음) |
| DELETE(미커밋) 중 POST | POST가 DELETE 커밋을 기다린 뒤 새 리뷰 201 |
| 잠금 대기 중 대상이 삭제되고 새 리뷰가 커밋됨 | 3의 재조회가 새 리뷰를 찾아 409 |

**보장**
- 같은 사용자·작품의 리뷰는 언제나 0개 또는 1개입니다.
- 같은 리뷰 상태(`reviewId`·`version`)를 보고 만든 변경 요청은 최대 하나만 반영됩니다.
- 오래된 요청은 다른(새) 리뷰를 바꾸거나 지우지 않습니다.
- 남는 본문은 실제로 요청된 값 중 하나이며 섞이지 않습니다. `updated_at ≥ created_at`.

**보장하지 않음**
- 목록·내 리뷰 응답이 서로 같은 시점이라는 것(별도 요청).
- 응답 이후의 상태. 각 응답은 그 요청이 처리된 시점의 결과입니다.

## 5. API

### 5.1 공통

- **[기존]** prefix `/api/v1`, `ApiResponse`, 세션 쿠키 인증, 변경 요청 CSRF(`X-XSRF-TOKEN`) 필수, 알 수 없는 본문 필드 무시.
- **보안 규칙 확인**: `WebSecurityConfig`의 `GET /api/v1/works/**` `permitAll`이 `GET /api/v1/works/{workId}/reviews`를 포함합니다. `/api/v1/me/reviews/**`는 "그 밖의 요청: 로그인 필요"에 해당합니다. 그래서 보안 설정은 바꾸지 않았고, 익명 공개 GET 200·익명 `/me` 401·CSRF 403을 통합 테스트로 확인합니다. `/works/**`의 공개 규칙은 GET만이므로 같은 경로의 다른 메서드는 공개되지 않습니다.
- **[기존]** 사용자 ID는 `@AuthenticationPrincipal AuthenticatedUser`의 `id()`로만 얻습니다. 경로·쿼리·본문의 사용자 ID는 받지 않습니다.
- **[기존]** ID는 JSON 숫자(Java `Long`)입니다. 요청의 `reviewId`·`version`도 JSON 정수 **숫자**로 보내야 합니다(문자열 거절). 프론트는 무손실 파서로 읽은 십진수 문자열을 그대로 JSON 숫자로 써서 보냅니다. 응답 `version`도 JSON 숫자이며 2^53을 넘을 수 있는 값으로 취급해 프론트 무손실 파서 정확 키에 추가합니다(화면 단계).
- 처리 순서: 인증(401)·CSRF(403) → 입력 검증(400, 오류를 모아서) → 작품 존재(404) → 리뷰 상태(404·409) → 실행

### 5.2 엔드포인트

| 메서드 | 경로 | 인증 | 성공 | 설명 |
|---|---|---|---|---|
| GET | `/works/{workId}/reviews?page&size` | 없음 | 200 | 공개 목록 |
| GET | `/me/reviews/{workId}` | 로그인 | 200 | 내 리뷰. 미작성이면 `review: null` |
| POST | `/me/reviews/{workId}` | 로그인 + CSRF | 201, `Location: /api/v1/me/reviews/{workId}` | 작성 |
| PUT | `/me/reviews/{workId}` | 로그인 + CSRF | 200 | 수정 (전체 교체) |
| DELETE | `/me/reviews/{workId}?reviewId=&version=` | 로그인 + CSRF | 204 | 삭제. 현재 리뷰가 없으면 204 |

요청 본문:

| 필드 | POST | PUT | 규칙 |
|---|---|---|---|
| `body` | 필수 | 필수 | JSON 문자열, §1.2 |
| `containsSpoiler` | 필수 | 필수 | JSON 불리언. 누락·`null`은 "스포일러 여부를 선택해 주세요.", 그 밖의 형식(`"true"`, `1`)은 "스포일러 여부는 true 또는 false여야 합니다." |
| `reviewId` | — (무시) | 필수 | JSON 정수, 1 이상, Long 범위 |
| `version` | — (무시) | 필수 | JSON 정수, 0 이상, Long 범위 |

DELETE query: `reviewId`(1 이상), `version`(0 이상) 필수. 누락·숫자 아님·범위 밖은 400.

예시:

```http
POST /api/v1/me/reviews/21
Content-Type: application/json
X-XSRF-TOKEN: …

{"body":"그림체가 좋다.\n결말은 아쉽다.","containsSpoiler":false}
```

```http
PUT /api/v1/me/reviews/21

{"reviewId":7,"version":0,"body":"그림체가 좋다.\n결말도 납득된다.","containsSpoiler":true}
```

```http
DELETE /api/v1/me/reviews/21?reviewId=7&version=1
```

내 리뷰 `data` (GET·POST·PUT):

```json
{ "workId": 21, "review": { "id": 7, "body": "그림체가 좋다.\n결말도 납득된다.", "containsSpoiler": true, "version": 1,
  "createdAt": "2026-10-08T06:00:00.123456Z", "updatedAt": "2026-10-08T06:10:00.654321Z", "edited": true } }
{ "workId": 21, "review": null }
```

공개 목록 `data`:

```json
{ "content": [
    { "id": 7, "author": { "nickname": "독자" }, "body": "그림체가 좋다.\n결말도 납득된다.", "containsSpoiler": true,
      "createdAt": "2026-10-08T06:00:00.123456Z", "updatedAt": "2026-10-08T06:10:00.654321Z", "edited": true }
  ], "page": 0, "size": 10, "totalElements": 1, "totalPages": 1, "hasNext": false }
```

- 공개 목록에는 작성자 사용자 ID·이메일·역할, 리뷰 `version`을 넣지 않습니다. 닉네임은 **[기존]** 중복을 허용하므로 같은 닉네임이 여러 명일 수 있습니다.
- **공개 목록은 로그인 여부와 관계없이 같은 응답입니다**(사용자별 필드 없음). 화면은 내 리뷰 `id`와 비교해 "내 리뷰"를 표시합니다.
- **스포일러 리뷰도 `body`를 포함합니다**(§1.3). `containsSpoiler`는 화면이 접어 보여 줄지 정하는 표시 정보입니다.
- 시각은 **[기존]** UTC ISO-8601(마이크로초)입니다.

### 5.3 DELETE 응답 계약

- 204는 "요청이 끝난 시점에 요청한 리뷰(`reviewId`)가 없다"는 뜻입니다. 이 요청이 지웠거나 이미 없었던 경우입니다. 본문이 없습니다.
- 409는 "현재 리뷰가 요청한 리뷰·버전과 다르다(지우지 않았다)"는 뜻입니다.
- 화면은 삭제 응답(204·409·오류)으로 **삭제 결과**를 판단하고, 이어지는 재조회 실패는 별도로 안내합니다. 재조회가 실패해도 삭제를 실패로 표시하거나 DELETE를 다시 보내지 않습니다.

### 5.4 오류

| 상황 | 상태 | `error.code` |
|---|---|---|
| 비로그인·세션 만료 (`/me/reviews/**`) | 401 | `UNAUTHORIZED` (**[기존]**) |
| CSRF 누락·불일치 (POST·PUT·DELETE) | 403 | `INVALID_CSRF_TOKEN` (**[기존]**) |
| 본문·스포일러·`reviewId`·`version` 입력 오류, 잘못된 `page`·`size` | 400 | `INVALID_INPUT` (해당 `fieldErrors`) |
| 본문이 JSON이 아님 | 400 | `INVALID_INPUT` "요청 본문을 읽을 수 없습니다." (**[기존]**) |
| `workId`가 숫자가 아니거나 Long 범위 밖 | 400 | `INVALID_INPUT` (`fieldErrors[workId]`, **[기존]**) |
| 없는 작품, `workId` ≤ 0 (공개 목록 포함 모든 리뷰 API) | 404 | `WORK_NOT_FOUND` (**[기존]**) |
| 이미 리뷰가 있는데 POST | 409 | `REVIEW_ALREADY_EXISTS` |
| 리뷰가 없는데 PUT | 404 | `REVIEW_NOT_FOUND` |
| 현재 리뷰와 `reviewId` 또는 `version`이 다름 (PUT·DELETE) | 409 | `REVIEW_VERSION_CONFLICT` |
| 리뷰가 없는데 GET | 200 | `review: null` |
| 리뷰가 없는데 DELETE | 204 | — |

### 5.5 권한

- **[확정]** USER와 ADMIN 모두 **자기 리뷰만** 작성·수정·삭제합니다. API는 세션 사용자 + 작품으로만 리뷰를 찾으므로 다른 사용자 리뷰를 가리킬 방법이 없습니다. 다른 사용자의 `reviewId`를 보내도 내 현재 리뷰와 비교될 뿐이라 내 리뷰가 있으면 409, 없으면 PUT 404·DELETE 204이고, 다른 사용자 리뷰는 바뀌지 않습니다.
- ADMIN의 리뷰도 일반 리뷰와 같이 공개 목록에 나오며 역할은 표시하지 않습니다.
- 관리자 moderation(다른 사용자 리뷰 숨김·삭제, 신고 처리)은 별도 후속 기능입니다.

## 6. 화면 (후속 구현)

### 6.1 배치와 조회

- 작품 상세: 작품 정보 → 별점(**[기존]**) → 내 리뷰 → 리뷰 목록("리뷰 N개") → 크레딧.
- 서버 렌더링에서 공개 목록(쿠키 전달 없음, `no-store`)과, 로그인했을 때만 내 리뷰(세션 쿠키만 전달, `no-store`)를 작품 조회와 병렬로 읽습니다.
- 목록 페이지는 상세 쿼리 `reviewPage`(1부터)입니다. 기존 `from`은 유지합니다. 잘못된 값·중복 값은 `reviewPage`를 뺀 주소로 307입니다.
- 리뷰 목록 조회만 실패하면 작품 상세는 보여 주고 리뷰 영역에만 "리뷰를 불러오지 못했습니다 · 다시 시도"를 표시합니다.

### 6.2 내 리뷰 영역

| 상태 | 표시 |
|---|---|
| 비로그인 | "리뷰를 쓰려면 로그인하세요" + 현재 상세로 돌아오는 검증된 `returnTo` |
| 리뷰 없음 | `textarea`("리뷰 내용"), 글자 수 "0 / 2,000"(코드 포인트), "스포일러 포함" 체크박스, "등록" 버튼 |
| 리뷰 있음 | 내 본문(접지 않음), 작성·수정 시각, "수정"·"삭제" |
| 수정 중 | 같은 폼에 기존 값, "수정 저장"·"취소" |
| 내 리뷰 조회 실패 | "내 리뷰를 불러오지 못했습니다 · 다시 불러오기" (작성 폼을 보여 주지 않음) |

- 명시적 저장 버튼으로만 요청합니다. 내용이 비었거나 기존과 같으면 저장 버튼을 비활성화합니다.
- 삭제는 같은 자리의 2단계 확인(브라우저 `confirm` 미사용)입니다.
- 중복 제출 방지: **[기존]** 별점의 mutation-lock 방식. 재조회가 끝날 때까지 변경 버튼 비활성.
- 저장하지 않은 입력이 있으면 이탈 경고를 띄웁니다.
- **[확정]** 작성 중인 글은 화면(메모리)에만 두고 localStorage·sessionStorage·URL에 저장하지 않습니다.

| 성공 후 재조회 실패 | 성공 안내는 유지하고 "최신 리뷰 정보를 불러오지 못했습니다 · 다시 불러오기". 변경 요청 반복 없음 |
| 400 | 오류를 입력에 `aria-describedby`·`aria-invalid`로 연결, 입력 유지 |
| 401 | 세션 만료 안내 + `reason=expired` 로그인 링크. 작성 중인 글은 화면에 남기고 이동하면 사라진다는 점과 복사를 안내 |
| 403 CSRF | **[기존]** 1회 재시도 후 실패하면 새로고침 안내 |
| 404 작품 | "작품을 찾을 수 없습니다. 삭제되었을 수 있습니다." |
| 409 이미 작성됨 | 내 리뷰를 다시 불러오고, 작성 중이던 글은 따로 남겨 복사할 수 있게 함 |
| 404 리뷰 없음(PUT) | "리뷰가 이미 삭제되었습니다." 작성 중인 글 유지 + "새 리뷰로 등록" |
| 409 버전 충돌 | "다른 곳에서 리뷰가 수정되었거나 삭제 후 다시 작성되었습니다." 작성 중인 글 유지, 최신 내용을 함께 보여 주고 "최신 내용으로 바꾸기" / "내 내용으로 다시 저장"(최신 `reviewId`·`version`으로 명시적 재요청) 선택 |
| 연결 실패·5xx | 변경 요청을 다시 보내지 않고 내 리뷰만 다시 조회. 작성 중인 글 유지 |

### 6.4 리뷰 목록·접근성

- 항목: 닉네임(없으면 "알 수 없는 사용자"), 작성 시각, "(수정됨)", 본문 또는 스포일러 안내, 내 리뷰 표시.
- 시각: `<time dateTime>` + `Asia/Seoul` 고정 형식.
- 스포일러: "스포일러가 포함된 리뷰입니다 · 내용 보기"(`aria-expanded`, `aria-controls`). 접힌 동안 본문을 렌더링하지 않음.
- 닉네임·본문은 React 텍스트로만 출력, `overflow-wrap: anywhere`로 모바일 가로 넘침 방지.
- 네이티브 컨트롤, 키보드만으로 사용 가능, 모바일 360px 한 열·버튼 44px 이상.
- 글자 수 표시는 입력과 `aria-describedby`로 연결하고 매 입력마다 읽지 않음.
