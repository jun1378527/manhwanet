## 1. 점수

- **[확정]** 0.5~5.0점, 0.5 간격입니다. 0점은 없습니다.
- "평가하지 않음"은 값이 아니라 **행이 없는 상태**입니다. 삭제하면 행을 지웁니다. 평균·참여자 수에 섞이지 않습니다.
- DB에는 반 점 단위 정수 `score_half`(1~10)를 저장합니다.
  - Java 엔티티는 `short scoreHalf`, API 경계는 `BigDecimal score`(scale 1)입니다. 변환은 `RatingScore`가 맡습니다.
  - JSON은 숫자 `4.5`입니다. 0.5 배수는 IEEE 754 이진수로 정확히 표현되므로 브라우저 `number`로 읽어도 오차가 없습니다.

### 1.1 요청 점수 검증

| 입력 `score` | 결과 |
|---|---|
| JSON 숫자이고 0.5의 배수이며 0.5~5.0 (`4.5`, `4.50`, `5`, `0.5`, `1E+0`) | 허용 |
| 누락, `null`, 본문이 비었거나 JSON `null` | 400 `INVALID_INPUT`, `fieldErrors[score]` "별점을 선택해 주세요." |
| 문자열(`"4.5"`), 불리언, 배열, 객체 | 400, "별점은 숫자여야 합니다." |
| 0, 음수, 5.0 초과, 0.5 배수가 아님(`4.25`, `4.50000000000000000001`) | 400, "별점은 0.5점부터 5.0점까지 0.5점 단위로 입력해 주세요." |
| 본문이 JSON이 아님 | 400 `INVALID_INPUT` "요청 본문을 읽을 수 없습니다." (**[기존]**) |

- 숫자는 JSON 원문을 `BigDecimal`로 정확히 읽어 검사합니다. `double`을 거치지 않으므로 `4.50000000000000000001`처럼 `double`로 바꾸면 4.5가 되는 값도 거절합니다.
- 문자열 거절은 Jackson의 기본 문자열→숫자 변환을 쓰지 않고, `score` 필드 전용 역직렬화에서 JSON 토큰 종류를 확인해 구현합니다.
- 본문의 다른 필드(예: `userId`)는 무시합니다(**[기존]** 알 수 없는 필드 무시).

## 2. 데이터 모델 — `V4__create_work_ratings.sql`

```sql
CREATE TABLE work_ratings (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id    BIGINT      NOT NULL,
    work_id    BIGINT      NOT NULL,
    score_half SMALLINT    NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_work_ratings_user FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE RESTRICT,
    CONSTRAINT fk_work_ratings_work FOREIGN KEY (work_id) REFERENCES works (id) ON DELETE CASCADE,
    CONSTRAINT ck_work_ratings_score_half CHECK (score_half BETWEEN 1 AND 10),
    CONSTRAINT ck_work_ratings_updated_at CHECK (updated_at >= created_at),
    CONSTRAINT uk_work_ratings_user_work UNIQUE (user_id, work_id)
);

CREATE INDEX idx_work_ratings_work_id ON work_ratings (work_id) INCLUDE (score_half);
```

| 요소 | 근거 |
|---|---|
| `uk_work_ratings_user_work` | 사용자·작품당 별점 1개를 DB가 보장. upsert의 충돌 대상. `user_id`가 앞이라 내 별점 조회에도 사용 |
| `idx_work_ratings_work_id` | 작품별 `COUNT`·`SUM` 집계를 인덱스만으로 읽음 |
| `ck_work_ratings_score_half` | 애플리케이션을 우회한 값도 거절 |
| `ck_work_ratings_updated_at` | 시각 정책(§2.1)을 DB가 보장 |
| 작품 FK CASCADE | 별점은 작품에 딸린 데이터. **[기존]** `work_titles`, `work_creators`와 같음. 작품 삭제 API는 아직 없음 |
| 사용자 FK RESTRICT | 회원 탈퇴 정책 전까지 별점이 있는 사용자 삭제를 막음 |

- **[기존]** V1~V3는 수정하지 않습니다. 다른 도메인은 ID 값으로만 참조합니다(`userId`, `workId`).
- 쓰기는 모두 SQL(§6)로 하므로 엔티티 `WorkRating`은 읽기 전용입니다. JPA Auditing(`BaseTimeEntity`)을 쓰지 않습니다.

### 2.1 시각 정책

| 동작 | `created_at` | `updated_at` |
|---|---|---|
| 처음 등록(행 없음 → INSERT) | 등록 시각 | 등록 시각(= `created_at`) |
| 다른 점수로 수정 | 유지 | 수정 시각. 단 기존 값보다 작아지지 않음(`GREATEST`) |
| 같은 점수로 다시 PUT | 유지 | 유지 (점수가 바뀌지 않았으므로) |
| 삭제 | 행 삭제 | 행 삭제 |
| 삭제 후 다시 등록 | 새 등록 시각 | 새 등록 시각 |

- 시각은 PostgreSQL `now()`(그 트랜잭션의 시작 시각)입니다. 동시 요청에서는 나중에 반영된 트랜잭션이 더 먼저 시작했을 수 있으므로, 수정 시 `GREATEST(기존 updated_at, now())`로 되돌아가지 않게 합니다. 이 때문에 `updated_at`은 "마지막 반영 트랜잭션의 시작 시각과 기존 값 중 큰 값"입니다.

## 3. 패키지와 의존 방향

```
rating ──▶ work    (WorkService.exists, WorkRatingSummaryQuery 구현)
rating ──▶ auth    (AuthenticatedUser.id())
work   ──✗ rating  (work 는 rating 을 import 하지 않음)
```

| 위치 | 타입 | 역할 |
|---|---|---|
| `work.application` | `WorkRatingSummaryQuery` (interface) | 메서드 1개: `Map<Long, RatingSummaryResponse> findByWorkIds(Collection<Long> workIds)`. 별점이 없는 작품은 결과에 없음 |
| `work.dto` | `RatingSummaryResponse(BigDecimal average, long count)` | 공개 응답 모양. `EMPTY = (null, 0)` |
| `work.application` | `WorkService.exists(Long)` | 작품 존재 확인(공개 메서드) |
| `rating.application` | `RatingSummaryQueryService implements WorkRatingSummaryQuery` | 집계 SQL 1개 실행 + 평균 계산. `WorkRatingRepository`에만 의존 |
| `rating.application` | `RatingService` | 내 별점 조회·저장·삭제. `WorkService`, `WorkRatingRepository`에 의존 |

- 인터페이스는 `work`가 필요한 기능(작품 ID들 → 공개 집계) 하나만 정의합니다. 범용 확장 지점(여러 구현, 등록 구조, 플러그인)은 만들지 않습니다. 구현체는 하나이며, 도메인 순환을 끊는 목적입니다.
- Spring 빈 순환도 없습니다. `WorkService → WorkRatingSummaryQuery(RatingSummaryQueryService) → WorkRatingRepository`, `RatingService → WorkService`.

## 4. API

### 4.1 공통

- **[기존]** prefix `/api/v1`, `ApiResponse`, 세션 쿠키 인증, 변경 요청 CSRF(`X-XSRF-TOKEN`) 필수. `/api/v1/me/**`는 보안 규칙의 "그 밖의 요청: 로그인 필요"에 해당하므로 보안 설정을 바꾸지 않습니다.
- **[확정]** 사용자 ID는 `@AuthenticationPrincipal AuthenticatedUser`의 `id()`로만 얻습니다. 경로·쿼리·본문의 사용자 ID는 받지 않습니다.
- 처리 순서: 인증(401)·CSRF(403) → 입력 검증(400) → 작품 존재(404) → 실행

### 4.2 엔드포인트

| 메서드 | 경로 | 성공 | 설명 |
|---|---|---|---|
| GET | `/me/ratings/{workId}` | 200 | 내 별점. 평가하지 않았으면 `score: null` |
| PUT | `/me/ratings/{workId}` | 200 | 등록·수정 통합. 본문 `{"score": 4.5}` |
| DELETE | `/me/ratings/{workId}` | 204 | 삭제. 평가하지 않은 상태여도 204 |

응답 `data` (GET·PUT):

```json
{ "workId": 21, "score": 4.5, "createdAt": "2026-10-07T06:00:00.123456Z", "updatedAt": "2026-10-07T06:10:00.654321Z" }
{ "workId": 21, "score": null, "createdAt": null, "updatedAt": null }
```

- PUT 응답은 **그 요청의 SQL이 기록한 값**입니다. 동시에 다른 요청이 바로 덮어쓸 수 있으므로 "현재 최종 값"을 보장하지 않습니다(§6).
- `workId`는 **[기존]** 다른 ID처럼 JSON 숫자(Java `Long`)입니다. 프론트는 무손실 파서 정확 키에 `workId`를 추가해야 합니다(프론트 단계).

### 4.3 오류

| 상황 | 상태 | `error.code` |
|---|---|---|
| 비로그인·세션 만료 | 401 | `UNAUTHORIZED` |
| CSRF 누락·불일치 (PUT·DELETE) | 403 | `INVALID_CSRF_TOKEN` |
| 없는 작품, `workId` ≤ 0 (GET·PUT·DELETE) | 404 | `WORK_NOT_FOUND` |
| `workId`가 숫자가 아니거나 Long 범위 밖 | 400 | `INVALID_INPUT` (`fieldErrors[workId]`) |
| 점수 오류(§1.1) | 400 | `INVALID_INPUT` (`fieldErrors[score]`) |
| `X-Expected-User-Id` 누락(PUT·DELETE)·형식 오류 | 400 | `INVALID_INPUT` (`fieldErrors[expectedUserId]`) |
| `X-Expected-User-Id`가 이 요청의 세션 사용자와 다름 | 409 | `USER_MISMATCH` (아무것도 바꾸지 않음) |

- 존재 확인과 저장 사이에 작품이 삭제되면 FK `fk_work_ratings_work` 위반이 납니다. **[기존]** 예상한 이름의 제약만 변환하는 규칙에 따라 이 제약만 404 `WORK_NOT_FOUND`로 바꾸고 나머지 무결성 오류는 500으로 둡니다.

### 4.4 권한

- USER와 ADMIN 모두 자기 별점만 조회·변경합니다. 다른 사용자 별점을 다루는 API는 없습니다.
- PUT·DELETE는 헤더 `X-Expected-User-Id`(화면을 렌더링한 사용자 ID, 십진수 문자열)가 필수입니다. 값은 이 요청의 세션 사용자와 비교하는 데만 쓰고, 별점 소유자는 세션 사용자입니다. 다르면 409 `USER_MISMATCH`이고 어느 계정의 별점도 바꾸지 않습니다. GET은 헤더가 있을 때만 확인합니다.
- ADMIN의 별점도 집계에 포함합니다.

## 5. 공개 집계

### 5.1 의미와 계산

| 값 | 정의 |
|---|---|
| `count` | 그 작품에 현재 별점이 있는 사용자 수(행 수) |
| `average` | 현재 별점의 산술 평균, 소수 첫째 자리 HALF_UP. `count`가 0이면 `null` |

- 한 SQL에서 `COUNT(*)`와 `SUM(score_half)`를 함께 읽습니다. 두 값은 같은 문장의 같은 스냅샷이므로 서로 어긋나지 않습니다.

```sql
SELECT work_id, COUNT(*), SUM(score_half)
FROM work_ratings
WHERE work_id IN (:workIds)
GROUP BY work_id
```

- 평균: `BigDecimal.valueOf(sum).divide(BigDecimal.valueOf(count).multiply(2), 1, RoundingMode.HALF_UP)`. 정수만 오가므로 오차가 없습니다. 예: `score_half` 합 17, 2명 → 4.25 → **4.3**
- 응답: `"rating": { "average": 4.3, "count": 2 }`, 별점 없음 `"rating": { "average": null, "count": 0 }`

### 5.2 조회 (N+1 없음)

- 목록: **[기존]** 작품 페이지 조회 뒤 페이지 단위 `IN` 일괄 조회 방식에 위 SQL 1개를 더합니다. 페이지가 비면 집계 SQL을 실행하지 않습니다.
- 상세: 같은 메서드에 ID 1개를 넘깁니다.
- 작품 등록 API 응답은 새 작품이므로 집계 SQL 없이 `rating: {null, 0}`을 넣습니다.
- 별점 수가 늘어도 목록·상세의 SQL 수는 같아야 합니다(`WorkQueryCountTest`로 검증).
- 사전 집계·랭킹 알고리즘은 후속 범위입니다.

### 5.3 시점 차이

- 내 별점(`/me/ratings/{workId}`)과 공개 집계(작품 목록·상세)는 **별도 요청**입니다. 두 요청 사이에 다른 사용자가 별점을 바꾸거나, 내 저장이 아직 반영되지 않았거나 이미 반영된 상태로 각각 읽힐 수 있습니다. 화면은 두 값이 같은 시점이라고 가정하지 않습니다(예: 내 별점을 저장한 직후 평균을 다시 불러옴).
- 작품 목록·상세 요청 안에서도 작품 정보와 집계는 읽기 전용 트랜잭션의 서로 다른 SQL입니다(READ COMMITTED). 평균과 참여자 수는 한 SQL에서 계산되므로 서로는 항상 일치합니다.

## 6. 동시성

### 6.1 쓰기 SQL

PUT (작품 존재 확인과 같은 트랜잭션, 한 문장):

```sql
INSERT INTO work_ratings (user_id, work_id, score_half, created_at, updated_at)
VALUES (:userId, :workId, :scoreHalf, now(), now())
ON CONFLICT ON CONSTRAINT uk_work_ratings_user_work DO UPDATE
SET score_half = EXCLUDED.score_half,
    updated_at = CASE WHEN work_ratings.score_half = EXCLUDED.score_half
                      THEN work_ratings.updated_at
                      ELSE GREATEST(work_ratings.updated_at, now()) END
```

- 응답은 같은 트랜잭션에서 그 행을 다시 읽어 만듭니다. upsert가 잡은 행 잠금은 커밋까지 유지되므로 다시 읽은 값은 이 요청이 기록한 값입니다.

DELETE: `DELETE FROM work_ratings WHERE user_id = :userId AND work_id = :workId` (지운 행 수와 관계없이 204)

- 격리 수준은 **[기존]** PostgreSQL 기본값 READ COMMITTED입니다.

### 6.2 보장하는 것과 보장하지 않는 것

**보장**
- 같은 사용자·작품의 행은 언제나 0개 또는 1개입니다(유니크 제약).
- PUT은 동시 실행에서도 유니크 위반 오류 없이 INSERT 또는 UPDATE 중 하나로 끝납니다. PostgreSQL 문서: `ON CONFLICT DO UPDATE`는 독립적인 오류가 없으면 높은 동시성에서도 둘 중 하나의 결과를 보장합니다.
- 남는 점수는 실제로 요청된 값 중 하나입니다. 섞인 값이나 중간 상태는 없습니다.
- `updated_at ≥ created_at`(DB CHECK)

**보장하지 않음**
- "마지막에 보낸 요청" 또는 "마지막에 도착한 요청"의 값이 남는다는 것. 남는 값은 DB가 행 잠금으로 반영한 순서에서 마지막 것이며, 그 순서는 클라이언트가 보낸 순서·서버 도착 순서·응답 순서와 일치하지 않을 수 있습니다.
- PUT·DELETE 응답이 "현재 최종 상태"라는 것. 각 응답은 그 요청의 SQL 결과일 뿐입니다.

### 6.3 경쟁별 가능한 결과

| 경쟁 | 진행 | 최종 상태 |
|---|---|---|
| 동시 PUT a, b (행 없음) | 먼저 INSERT한 쪽이 커밋할 때까지 다른 쪽이 기다린 뒤 UPDATE | 행 1개, 점수는 a 또는 b. 두 요청 모두 200 |
| 동시 PUT a, b (행 있음) | 행 잠금으로 직렬화 | 행 1개, 점수는 a 또는 b. 두 요청 모두 200 |
| PUT(수정)이 먼저 잠금, DELETE 대기 | DELETE가 커밋된 새 행을 다시 확인해 삭제 | 행 없음 |
| DELETE가 먼저 잠금, PUT 대기 | 행이 사라진 뒤 PUT이 INSERT로 다시 시도 | 행 1개(새 `created_at`) |
| PUT(INSERT) 미커밋 중 DELETE | DELETE는 아직 보이지 않는 행을 기다리지 않고 0행 삭제 후 204 | PUT 커밋 후 행 1개. **DELETE가 나중에 끝났어도 행이 남을 수 있음** |

- 같은 화면 안의 순서 꼬임은 화면이 저장 중 추가 제출을 막아 줄입니다(화면 단계).
